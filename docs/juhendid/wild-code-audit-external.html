Kavitro Plugin Findings 244 Python files, 73 GraphQL documents, 286 commits of history

Static review of the plugin source, its release pipeline and its full git history, commissioned by Mailabl as the operator of the API this plugin consumes. Nineteen issues, each traced from the value that carries it to the call that consumes it. Nothing was executed and no live endpoint was touched.

The common thread. The plugin treats every API response as trusted input. Filenames, file extensions, folder paths, project names and description HTML all arrive over GraphQL and flow into a shell, a filesystem path, an OS file handler or a rich-text renderer with no validation in between. Those values are authored by people: a filename comes from whoever uploaded the attachment, a project name from whoever typed it, a description from whoever wrote it. A desktop client has to treat them the way it would treat a downloaded file, regardless of what any server does with them on the way in. Most of the high findings are the same fix repeated at a different boundary.

API data reaching dangerous sinks 5 findings

HighWC-01

A folder path from the API is passed to a shell

utils/Folders/foldersHelpers.py:166-174 
target = file_path.replace("/", "\\")
if target.lower().startswith("http"):
    subprocess.Popen(["start", "", target], shell=True)
else:
    subprocess.Popen(["explorer", target], shell=True)

Chain. The GraphQL field filesPath (on projects, contracts, coordinations and easements) reaches extract_files_path in python/responses.py:215, becomes the payload of the folder button in widgets/DataDisplayWidgets/module_action_buttons.py:118, and goes straight to open_item_folder on click. Nothing filters, quotes or allowlists it.

Why the shell matters. On Windows, Popen(list, shell=True) joins the list with list2cmdline and hands the result to cmd.exe /c. list2cmdline quotes for whitespace and embedded quotes only; it leaves & | < > ^ alone. A space-free value such as C:\x&calc.exe survives unquoted into cmd and the part after the & executes. On POSIX the extra list items become $0 and $1, so this is Windows-only, which is also the only platform the function targets.

Worth noting that the plugin writes this field back itself (foldersHelpers.py:88-105 sends {"filesPath": link}), so the value round-trips through storage. A value set on one workstation is executed on another.

FixDrop shell=True and use os.startfile(path) for directories, or QDesktopServices.openUrl(QUrl.fromLocalFile(path)). Reject anything that is not an existing local directory before opening it, and reject UNC paths unless you specifically intend to support them.
HighWC-02

The API picks the file extension, the OS picks what to run

widgets/DataDisplayWidgets/TaskFilePreviewDialog.py:194-215, 170-176 
ext = str(data.get("ext") or "").strip().lower().lstrip(".")
suffix = f".{ext}" if ext else os.path.splitext(file_name)[1]
handle = tempfile.NamedTemporaryFile(delete=False, suffix=suffix)
...
if hasattr(os, "startfile"):
    os.startfile(normalized_path)

Chain. ext, fileName and mimeType come from taskFiles.graphql:26-28, attached to a task by an uploader. The attachment bytes are streamed into a temp file whose suffix is that extension, and the "open externally" button (:864) hands the file to the OS default handler. There is no extension allowlist anywhere in the file and no confirmation step. On Windows os.startfile executes .exe, .bat, .cmd, .hta and .scr directly.

The fallback is the sharper edge. When ext is absent or null, line 196 falls back to os.path.splitext(file_name)[1], and fileName is a user-supplied original filename. Treat both fields as attacker-controlled, and note that they fail differently: an allowlist on ext alone still leaves the fileName path open whenever ext comes back empty. Assume it will.

Partly dormant, worth knowing. open_preview at :96 can reach this without a click, but FORCE_EXTERNAL_EXTENSIONS and FORCE_EXTERNAL_MIME_TYPES are both empty sets (:57-58), so that branch is currently unreachable. Populating either set turns a click-gated issue into an automatic one, so please add the allowlist before adding entries there.

Beyond executables: html and svg extensions open attacker-authored content in the user's default browser, which is worth blocking too even though it is not code execution on the desktop.

FixAllowlist previewable extensions, derive the suffix from that allowlist rather than from either API field, strip path separators from both ext and fileName, and confirm with the user before handing anything to the OS handler.
HighWC-03

A project name from the API becomes a copy destination, unchecked

utils/Folders/foldersHelpers.py:44-53 
folder_name = FolderNameGenerator().folder_structure_name_order(project_name, project_number)
dest_dir = os.path.join(target_folder, folder_name)
if os.path.exists(dest_dir):
    ...warn...
else:
    shutil.copytree(source_folder, dest_dir)

Chain. project_name and project_number come from extract_item_name and extract_project_number (python/responses.py:264-275), straight off the GraphQL node. folder_structure_name_order (:108-155) concatenates the parts with "".join and applies no filtering at all.

A .. segment escapes the configured target folder. The two Yes/No dialogs do not help, because the user confirms at line 33, before the name is generated at line 44, so the destination is never shown.

You already have the right helper for this elsewhere in the codebase: _safe_file_name in modules/easements/easement_pdf_service.py:400 is a proper character allowlist that collapses .. to a fallback.

FixSanitize folder_name to a single path component with that same helper, then assert the resolved dest_dir is still under target_folder before copying.
HighWC-04

Description HTML renders with external links enabled

widgets/DataDisplayWidgets/HtmlDescriptionWidget.py:21-22 
self.setOpenExternalLinks(True)
self.setOpenLinks(True)
...
self.setHtml(self.normalize_html(html or ""))

This QTextBrowser is built directly from API description HTML at TaskDetailOverviewWidget.py:310 and ExtraInfoWidget.py:126, 392. normalize_html (:36-70) only restyles <mark>, <table> and <blockquote>. It never inspects href and applies no tag or attribute allowlist.

Clicking a link therefore hands an author-chosen URI to Qt without an application-level decision. Local file and folder links are an intentional product feature, but the current implementation does not distinguish a local path from a Windows UNC or mapped network path and does not constrain registered custom schemes. A network path may initiate an SMB connection, while a custom scheme may invoke an operating-system handler. QTextBrowser has no JavaScript engine, so this stops short of script execution inside the description view.

Descriptions are authored by users, so the content should be treated as untrusted at render time regardless of what happens to it in transit or storage.

Implemented remediationControlled local file and folder opening remains a supported feature. The widget uses setOpenLinks(False) and setOpenExternalLinks(False), handles anchorClicked, and classifies every destination before filesystem access. It allows http and https after a destination confirmation. Supported local files open in the existing internal preview; only centrally allowlisted extensions can be handed to the operating system after a default-No confirmation. Local folders require confirmation. UNC, hosted file:// URLs and mapped network drives are detected before probing, receive a stronger network warning, and continue only after confirmation. All other schemes and file types are blocked. The remaining, user-approved local and network file-opening risk is an intentional product trade-off.
LowWC-15

The createDownloadLink mutation returns a url that goes straight into requests.get(url, stream=True) with redirects enabled. Credential and session handling 4 findings

The repo ships a written policy in safety.md: token-like secrets must go through the QGIS Authentication Manager, never plain settings. The implementation inverts it. The password, which nothing reads, goes into the encrypted store. The bearer token, which is used on every request, goes into a plaintext file.

HighWC-05

Bearer token written to plaintext QgsSettings

utils/SessionManager.py:100 
SESSION_TOKEN = "session/token"
...
settings.setValue(SESSION_TOKEN, SessionManager._instance.apiToken)

This is the live credential sent as Authorization: Bearer on every API call (api_client.py:82). QgsSettings persists to QGIS3.ini on Linux and macOS and to HKCU on Windows, in the clear. Anything that reads the user profile (a backup, a sync client, a support bundle, another local account) walks away with a working session for as long as the token remains valid.

The encrypted store is already wired up two methods below (save_credentials, :130). The token is the one credential that does not use it.

FixStore the token in the QgsAuthMethodConfig alongside the rest, keeping only the auth config id in settings, exactly as safety.md specifies.
MediumWC-07

Logging out never clears stored credentials

utils/SessionManager.py:183

clear_credentials() exists, removes the auth config and the settings keys, and is correct. It is also dead code, with zero callers anywhere in the tree.

SessionUIController.logout calls SessionManager.clear(), which only removes the session keys and sets a needs-login flag. The QgsAuthMethodConfig holding username, password and API key survives logout indefinitely, on a shared workstation as much as a personal one.

FixCall clear_credentials() from the logout path.
MediumWC-08

The password is stored, and then never used

utils/SessionManager.py:134

save_credentials writes username, password and apikey. Every caller of load_credentials() (easement_layer_service.py:419, projects_layer_service.py:227, works_layer_service.py:296, asbuilt_layer_service.py:243) reads only .username, which is already in settings under AUTH_USERNAME. self.password and self.api_key are never read by anything.

There is also no re-authentication path that could use them. The login mutation requests refreshToken and expiresIn (login_dialog.py:227-228) and discards both, so the token has no client-side expiry and is never renewed. It simply persists until a 401 comes back.

The API returns those two fields precisely so a client can renew without holding a password, and there is a refreshToken mutation for it. Adopting that path makes this finding disappear by deletion rather than by adding code.

FixStop storing the password. Store the token and its expiry, and renew through the existing refresh mutation.
MediumWC-09

The login mutation is built by string interpolation

login_dialog.py:223-231 
graphql = f'''
    mutation {{
        login(input: {{ username: "{username}", password: "{password}" }}) {{
            accessToken refreshToken expiresIn
        }}
    }}
'''

This is the only interpolated GraphQL document in the codebase. All 59 other call sites load a static .graphql file and pass runtime values through variables, which is the right pattern and is already available here: send_query is called with variables=None.

Why it matters, in order. First, because the secret sits in the query document rather than in variables, the plaintext password is carried by anything that records GraphQL query text: APM, tracing, error reporting, proxies, WAFs, and any request logging at either end. Query documents are routinely logged on the assumption that they contain no secrets. That assumption is normally correct and it is what makes this pattern dangerous. Variables, being a parsed key-value map, can be redacted structurally by key; a free-form document can only be scrubbed by pattern matching, which is inherently fragile.

Second, a password containing " or a trailing backslash produces a malformed document. _classify_login_error (:155-191) reports the resulting parse failure as a generic "server unavailable", so affected users cannot log in and have no way to find out why.

The injection framing is weaker than it looks and worth stating plainly: the person typing into the dialog is the local user, who could already send arbitrary GraphQL to the same unauthenticated endpoint with curl. The injection grants them nothing new. The credential handling is the finding.

FixMove the mutation into a .graphql file and pass the credentials via variables, matching every other call site in the plugin.

HighWC-06

A credential file was committed and is still recoverable from history

modules/GptAssistant/ · dotenv file · commits 34b3217 to 855764a, 5-7 Aug 2025

A dotenv credential file was committed alongside an OpenAI client module and later deleted with the rest of that directory. Deleting it from the working tree does not remove it from history. It remains fetchable by anyone who clones this public repository.

What is known. The sibling logic/Gpt4oClient.py reads os.environ.get("OPENAI_API_KEY"), and the committed file matched an OPENAI_API_KEY-style assignment pattern. What is not. The file's contents were not read; the review tooling blocks reading credential files. As a partial signal, a scan of every blob across all 286 commits found zero matches for OpenAI, AWS, GitHub, Google or Slack key formats, or PEM private key headers, which suggests the stored value may have been a placeholder.

Also committed in that directory: __pycache__/*.pyc files, which preserve string literals independently of the source.

FixInspect that blob, rotate the key if it was ever live, then purge the path from history with git filter-repo and force-push. Treat it as compromised until verified otherwise.

Release pipeline 3 findings

One workflow, .github/workflows/qgis_release.yml. The trigger surface is sound: release: published and workflow_dispatch only, no pull_request_target, no untrusted PR checkout, and permissions scoped to contents: write rather than left at default. What follows are escalations from "can publish a release" to "can execute in the job that builds the artifact users install".

MediumWC-10

Release tag and inputs are interpolated straight into shell and Python

.github/workflows/qgis_release.yml:40, 43, 44, 46, 111, 208 
RELEASE_TAG="${{ github.event.release.tag_name }}"     # :40
RELEASE_VERSION="${{ inputs.release_version }}"        # :43

python - <<'PY'
release_version = "${{ steps.release_values.outputs.release_version }}".strip()   # :111

Git tag names permit $, backticks, ;, | and &. Actions expands ${{ }} before the shell ever sees the line, so the quoted heredoc at :107 stops bash expansion but not template expansion, and a crafted value lands inside the Python source.

The version guard at :60 does not close this. It runs after substitution, so it cannot protect the shell, and its own tail (([.-].*)?) permits arbitrary characters after a . or -. release_tag is never validated at all and flows unvalidated into :195 and :208.

FixPass values through env: and reference them as quoted shell variables, the way :203-205 already does correctly for the release body and title. Tighten the version regex tail and validate the tag. The same template is duplicated in MAIN_PLUGIN_RELEASE_SETUP.md:107-283 and needs the same fix.
MediumWC-11

Published plugin zip carries no checksum or signature

tools/qgis_repo_release.py:190-237

_write_plugins_xml emits version, download URL, author, changelog and a dozen other elements, and no hash of any kind. _build_zip (:162-173) produces the archive without a digest, and nothing in the workflow generates or verifies one. QGIS Plugin Manager installs on TLS alone, so anyone who can replace a release asset can swap the plugin undetectably.

FixEmit a SHA-256 of the zip into plugins.xml from _write_plugins_xml.
MediumWC-12

Unpinned build dependencies with credentials left on disk

.github/workflows/qgis_release.yml:24-25, 28, 33 
run: python -m pip install --upgrade pip qgis-plugin-ci   # :33
uses: actions/checkout@v5                                 # :25
uses: actions/setup-python@v6                             # :28

qgis-plugin-ci is installed with no version, no lockfile and no hash pinning, into the job that produces the artifact users install. A compromised release of it, or of any transitive dependency, executes there. The two actions are mutable tag refs rather than commit SHAs, which is lower risk since both are first-party.

Amplifying this: checkout has no with: block, so persist-credentials defaults on and the GITHUB_TOKEN sits in .git/config on the runner for the whole job. Any code execution in the job reads it straight off disk.

FixPin qgis-plugin-ci to a version, pin the actions to commit SHAs, and set persist-credentials: false.

Logging and temporary files 5 findings

MediumWC-13

Full HTTP error bodies are persisted to world-readable log files

python/api_client.py:113-118, 331-336 → Logs/python_fail_logger.py:155 
body = response.text
raise Exception(tag_message(ApiErrorKind.SERVER, template.format(error=body)))

The entire non-200 response body is embedded in the exception message. Those exceptions are forwarded to PythonFailLogger.log_exception from a dozen call sites (api_actions.py:466, 580, 710, 842, 898, 1012 among others), and log_exception writes str(exc) verbatim to disk. Whatever an error body happens to contain (session context, record data, echoed request payload, server-side stack traces) is persisted in plaintext on the user's machine.

Those logs land in Logs/PythonLogs/ and Logs/SwitchLogs/ inside the plugin directory. There is no os.chmod, no os.umask and no mode argument anywhere in the codebase, so files inherit the default umask, typically world-readable on Linux and macOS.

FixTruncate or omit response.text before it enters an exception that gets persisted, and create the log directory with restrictive permissions.
MediumWC-14

Predictable crash log opened for truncation at import time

main.py:28-33 
CRASH_LOG_PATH = os.path.join(tempfile.gettempdir(), "kavitro_crash.log")
_CRASH_LOG_HANDLE = open(CRASH_LOG_PATH, "w", encoding="utf-8")

Fixed name in a world-writable directory, opened "w" with no O_EXCL and no per-user subdirectory, at module import. On a shared Linux or macOS host another local user can pre-create the path as a symlink and have the plugin truncate a file the QGIS user owns. Modern kernels with fs.protected_symlinks block the classic version of this in sticky directories, which limits but does not eliminate it. Separately, faulthandler tracebacks land there readable by anyone.

Checked and sound 9 areas

Recorded both so the review is auditable and because several of these are places the code got it right on purpose.

  • No dynamic code execution. Zero uses of eval, exec, pickle, marshal, yaml.load or dynamic imports across all 244 files.
  • TLS is never weakened. No verify=False, no _create_unverified_context, no CERT_NONE. The endpoint is a hardcoded https:// URL in bundled config, and every http:// hit in the repo is an XML namespace or a QGIS DTD reference.
  • GraphQL is parameterized everywhere else. 59 of 60 call sites load a static .graphql file and pass data via variables, including the user search bar. The .graphql files contain no templating placeholders at all.
  • No archive extraction anywhere. No extractall, no tarfile. The only zip code is write-only in the release script, with every arcname derived from a relative_to call. No zip-slip surface.
  • Layer filter quoting is correct. MapHelpers._sql_quote and PropertyDataLoader._sql_quote both double single quotes properly before values reach setSubsetString and selectByExpression. Backslashes are not escaped, which would matter on MySQL but not on the OGR, SQLite and GeoPackage providers actually in use.
  • No secret is ever logged. Tokens, passwords, API keys and Authorization headers appear in no log file and no print. The one debug print in the auth path reports only the absence of a token.
  • Login errors do not leak server text. _classify_login_error deliberately maps raw server messages onto generic translated strings before display.
  • CI trigger surface is safe. No pull_request_target, no workflow_run, no untrusted PR checkout, and permissions narrowed to contents: write rather than left at default.
  • No hardcoded secrets in the working tree. Clean against PEM headers and AWS, GitHub, Slack, Google and OpenAI key formats, and against high-entropy literals. Everything the keyword sweep surfaced is a settings key name, a UI translation string, or NASA's public DEMO_KEY.
